# Architecture rules
- Multi-ranch expenses split one total in cents via repartirGastoRanchos, allow explicit allocations, and validate all destinations before creating ordinary per-ranch expenses; existing expenses are edited individually. Why: avoid duplicated totals and overwriting captured expenses.
- Weekly settlements append dated receipts with explicit per-trip amounts; calc.ts derives balances and reconciles legacy receipts. Admin-only corrections preserve originals and reasons and use conditional updates. Why: partial payments and duplicate corrections must retain evidence without overwriting concurrent changes.
- Conditional settlement writes use guardar-liquidacion.ts with serialized JSON filters. Why: PostgREST stringifies raw objects as invalid JSON instead of matching the stored receipt.
- Capture permissions and provider-operation guards live in roles.ts; shared collections use explicit updates for existing rows and database triggers enforce per-action and assigned-ranch scope. Why: an upsert invokes insert guards even when receiving an existing order.
- Engineers and ranch managers insert unevaluated harvest departures through the shared harvest provider; a database trigger reserves trip changes and deletion for admins. Why: departure access must not permit historical or financial changes.
- Departures store either bins or direct kg per lot; calc helpers validate, compare and allocate using that quantity without creating an evaluation. Why: field weights must remain distinct from frozen freezer receipts and legacy trips.
- New departures snapshot their transport checklist and origin labels, await the existing protected insert, then build pdf-salida.ts client-side using private photos; PdfSalida prepares files before sharing. Why: failed saves must not issue departure PDFs and reprints must preserve captured transport details.
- Field application advances reference explicit confirmed delivery sources; weekly leftover decisions use the shared Fase3 provider and never create receipts or replace the source. Why: partial receipts, returns and carryovers remain traceable without duplicate costs.
- Off-plan applications snapshot manually confirmed availability, dose and dated price in aplicaciones_campo; delayed deliveries reuse their original source. Why: extra applications preserve recipes and never duplicate an existing delivery or cost.
- Recipe variants support dated ranch inclusions or exclusions, with an empty table list meaning every table; display program tabs without table assignment controls. Product removal uses a pure calc helper and only changes the selected variant; retain old lot snapshots unless an authorized forward-only backfill replaces them. Why: package edits must not erase catalogs or captured history.
- Preparation backfills create idempotent pending pedidos linked through lote.insumos; arrivals retain overdue pending orders until received, and weekly receipt backfills use the existing demand keys. Why: future and overdue supplies remain actionable without duplicate charges or fabricated receipts.
- The executive panel reuses shared cost, consumption and expense allocation functions; date filters select planting/harvest cohorts and costs remain cumulative. Dirección receives read-only expense access, never result-screen access. Why: comparable denominators and no duplicated business math or new editing privileges.
- Parameter-based opening plant balances are marked on requests and charged once independently of receipts; normal receipt charges exclude them. Why: imported active lots can carry an authorized opening balance without fabricated tickets or duplicate costs.
- Keep all tables in the shared context and retire them with `Tabla.archivada`; operational filters and planting validation exclude retired tables, but historical and cost lookups retain them. Why: grouped imports must not duplicate available real tables or lose their records.
- Executive acreage separates planted in-cycle area, overdue harvest area and future planting; weekly harvest uses dated departures and frozen evaluations, while clearly labeled projections spread remaining yield goals over the 14-day harvest window. Why: planning area and estimates must never masquerade as active acreage or recorded harvest/payment.
- Operational acreage summaries and lists reuse filasSuperficieTablas/totalesSuperficieTablas, with one row per unclosed lot plus the table's free remainder; status subtotals use the unfiltered cohort and selection totals use selected statuses. Why: both views agree without counting a table's full area once per lot.- The Aplicaciones screen is view-only: consumption is assumed as received minus returned, pooled per ranch/product/week and split by programmed dose×ha via `consumoAsumidoAplicaciones`; PDF built client-side in `pdf-aplicaciones.ts`. Why: engineers only need a printable list; returns are captured in Devoluciones.
- Per-screen access (ver/capturar/editar/borrar) is `Acceso.permisos` in roles.ts; the DB maps collections to screens (`pantallas_de`/`tiene_permiso`) and `proteger_personalizado` enforces it, while legacy role rules apply only to users with non-admin roles. Why: one permission source for UI and database.
